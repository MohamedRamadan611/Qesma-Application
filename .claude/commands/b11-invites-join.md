Prerequisite: B10 merged. Skills (max 4): think-before-coding, idempotency-and-side-effects, security-discipline, data-modeling-discipline.

Step 0 (plan, wait for approval): the six-step design, and settle explicitly (Decision Log A-numbers continue):
1. **Secrets.** Code format (recommended: 8 chars, unambiguous 32-symbol alphabet, shown `XXXX-XXXX`, normalised on input; the Stitch design `DHB-4821` is too guessable, say so), link token (>= 128 bits from `SecureRandom`, only the SHA-256 stored, `token_hash` unique), constant-time lookup, how a code collision on insert is retried. Neither secret is ever logged (log invite id only) nor returned after creation except the code (admins need to re-read it: decide whether `GET /groups/{gid}/invites` returns the code and not the token).
2. **Preview vs enumeration.** `GET /invites/{codeOrToken}` is authenticated; define the exact response (group name, type, inviter display name, member count, unclaimed ghost `{id, name}` list, caller state: NONE / PENDING_APPROVAL / ALREADY_MEMBER). **No balances, no expense counts, no other members' accounts** (the design P12-02 shows amounts: omitted, explain why). Unknown code -> 404; expired/used-up -> 410 `INVITE_EXPIRED`; revoked -> 410 `INVITE_REVOKED`. Rate limit (per user and per IP) on lookup/join against code guessing; reuse the existing filter style, no new dependency (no Redis).
3. **Join transaction.** `POST /invites/{x}/join` with `{claimMemberId}` XOR `{newMemberName}`, `Idempotency-Key` (key write and business write in one transaction, A24-style replay returns the same result incl. status code). Concurrency: two users claiming the same ghost, one user joining twice, `max_uses` reached by parallel joins: decide the locking (recommended: `SELECT ... FOR UPDATE` on the invite row + DB unique indexes as the last defense) and the errors (`MEMBER_ALREADY_CLAIMED` 409, `ALREADY_MEMBER` 409, `DUPLICATE_MEMBER_NAME` 409). A claimed member keeps all history; a new member gets role MEMBER, status ACTIVE, `joined_at`, next `sort_order`/`member_seq`.
4. **Approval.** `requiresApproval` -> 202 `PENDING_APPROVAL` + a `join_requests` row; Admin/Owner `approve` (performs the same claim/create atomically, re-validating that the ghost is still free) or `reject`. What happens when the invite is revoked or expires while a request is pending (recommended: pending requests stay decidable until an admin acts, but no new requests).
5. **Admin operations.** `POST/GET/DELETE /groups/{gid}/invites` (permission `MANAGE_INVITES`), `GET /groups/{gid}/join-requests`, `POST .../approve|reject`, `POST /groups/{gid}/members/{mid}/unlink` (account removed, member and history kept, the user loses access; refuse for the OWNER member). Defaults: 7 days, max 30; `maxUses` optional.
6. Events: this prompt only **emits nothing yet** (B15 adds events); leave one clearly named hook (an interface call or a TODO-free no-op `GroupEventPublisher`) only if the plan justifies it, otherwise B15 retrofits. State the choice.

Implement: migration V13 (`group_invites`, `join_requests` with constraints from PHASE2_SPEC section 3, indexes for every FK and for lookup by code/token_hash), entities, repositories, `InviteService`/`JoinService` (`@Transactional` on service methods), controllers + DTO records, `ErrorCode` additions, OpenAPI operation ids + regenerate, README curl flow for two users (fake-auth), Decision Log, `docs/mobile-client.md` note.

Tests (Testcontainers): create/list/revoke authorization matrix (Owner/Admin ok, Member 403, stranger 404); preview never contains balances or account ids (assert the JSON field set); expired, revoked, exhausted, unknown; claim ghost, create new, duplicate name, already member, ghost claimed once under **parallel** joins (N threads, exactly one wins), `max_uses` under parallel joins, idempotent replay returns identical result and `Idempotency-Replayed`; approval path including approve of a ghost claimed meanwhile; rate limit on code guessing; token/code not present in logs (capture appender); unlink keeps history and balances; user who joined can then read the group and cannot read others (IDOR); B10 matrix extended with the new routes.
