Read AGENTS.md (rule 11: no new infrastructure or library without an ADR and the owner's approval), **docs/PHASE2_SPEC.md sections 3 (device_tokens), 8, 11**, docs/PROJECT_PHASES.md 2.7, docs/adr/ADR-001..008 (format), the `MailSender`/`NoopMailSender`/`DevConsoleMailSender`/`DevMailProdGuard` pattern, B15/B16 recorder and prefs. Prerequisite: B17 merged and a Firebase project exists (ask the owner; do not invent credentials). Skills (max 4): think-before-coding, idempotency-and-side-effects, observability-by-default, security-discipline.

Step 0 (plan, wait for approval): the six-step design, and write **ADR-010 "Push notifications via FCM"** first: why push at all in Phase 2, the boring alternative (in-app polling only), the dependency choice (verify on Maven Central and the official docs which Firebase Admin SDK version to pin; do not guess a version; consider the plain HTTP v1 API with a service account token via the existing HTTP stack instead of a heavy SDK), secrets handling (service-account JSON from environment/secret file, never in git or logs), failure behaviour. Wait for the owner's approval of the ADR before any code. Then settle:
1. **Delivery model.** After commit of the transaction that wrote a notification, send push asynchronously (a small scheduled dispatcher reading unsent committed notifications, or `@TransactionalEventListener(AFTER_COMMIT)` with a bounded executor: choose, justify, and state the at-least-once/duplicate behaviour and how the client dedupes by notification id). A push failure never fails the business request.
2. **Payload.** Minimal and non-sensitive: type, group id, notification id, deep-link target; **no names, titles or amounts in the push payload** unless the plan justifies it (recommended: a generic Arabic title/body rendered from type, details fetched by the app). Respect mute/global prefs (already applied at notification creation).
3. **Tokens.** `POST /devices {token, platform}` upsert by token (a token moves to the latest user), `DELETE /devices/{id}`, cleanup on logout and on FCM "unregistered/invalid" responses, `last_seen_at`, max tokens per user, purge of stale tokens. Account deletion (B17) already purges them: assert it.
4. **Config.** `qesma.push.enabled` default false; `local`/test profiles use a recording fake sender (like the mail fakes) with a prod guard so a prod profile cannot start with the fake; health/metrics: sent/failed counters, no token logged.

Implement: ADR, migration V19 (`device_tokens`), `PushSender` interface + FCM implementation + fake, dispatcher, device endpoints, config properties, guard, OpenAPI + ids, README (how to configure Firebase), Decision Log.
Tests: token upsert/move/delete and IDOR (cannot delete another user's token); fake sender receives exactly one push per eligible notification, none for muted users, none for the actor; invalid-token response removes the token (simulate through the fake); sender failure does not roll back or fail the business call; payload contains no names/amounts (assert); prod guard test; stale purge; B10 matrix extended. No test calls real FCM.
Constraints: follow AGENTS.md; optional prompt: the app must work fully without it (`push.enabled=false`); no secrets in git. Done when `./mvnw clean verify` passes. Then Stop protocol; tell the owner `mobile` must regenerate the client.
