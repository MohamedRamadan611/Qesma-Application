This is the highest-risk Phase 2 prompt because it touches **money presentation**. Test-first for every balance change; the pure engine stays pure.

Step 0 (plan, wait for approval): the six-step design, and settle (Decision Log):
1. **Balance rule.** Recommended: nets and suggested transfers count **CONFIRMED only**; PENDING and DISPUTED are informational. Define the exact new fields (per transfer: `pendingMinor` = sum of PENDING settlements between that exact from/to pair, `hasDispute`, and the id list needed by the UI to open them) and where computed (SQL totals vs engine). `Sum of nets = 0` must still hold. Say what the client may and may not do (it never subtracts pending amounts itself).
2. **State machine.** Implement the PHASE2_SPEC section 6 table as one structure (`from, action, actorRule -> to`), invalid -> `409 INVALID_STATE_TRANSITION` (new code). Repeating a transition already applied is a no-op returning the current view (no duplicate event/timestamp). Concurrency: two simultaneous confirm/cancel/dispute on the same row (recommended: optimistic `UPDATE ... WHERE status = ?` returning 0 rows -> reload and apply idempotency rule, or row lock; state which).
3. **Who may act.** Payer = `from` member's linked account; receiver = `to` member's; Admin/Owner may record on behalf (auto CONFIRMED + `recorded_by_admin`). A ghost (unlinked) member cannot confirm, so a settlement toward a ghost must be recordable by Admin/Owner as CONFIRMED (and a member declaring a payment to a ghost: decide: recommended allowed only through Admin/Owner).
4. **Migration V14.** Add status, timestamps, `created_by_member_id`, `recorded_by_admin`; **backfill all Phase 1 rows to CONFIRMED + recorded_by_admin = true** so balances do not change (prove with a test: balances before/after migration identical on seeded data). CHECK constraints tying status to timestamps (`confirmed_at` iff CONFIRMED, etc.).
5. **Phase 1 delete.** `DELETE /groups/{gid}/settlements/{sid}` (hard-ish delete, 204) conflicts with the ledger rule once there are statuses. Decide (recommended): remove it from the API and the OpenAPI document, replaced by `cancel`; CANCELLED rows stay in history. List the Phase 1 tests/mobile code affected and the version note for the client.
6. **`yourNetMinor`** and everything derived from totals (`YourNetQuery`, group summary) must use the same rule: CONFIRMED only. Add the engine/query filter in **one** place.

Implement: migration, entity/repository, `SettlementService` (declare, record-on-behalf, confirm, dispute, cancel, list with status filter), controller routes, `BalanceView` additions, totals queries filtered by status, engine tests/fixtures if the calculator input changes (shared fixtures in `/fixtures/*.json` get new vectors, existing vectors unchanged), OpenAPI + ids, seed (one PENDING and one DISPUTED example), Decision Log, README.
