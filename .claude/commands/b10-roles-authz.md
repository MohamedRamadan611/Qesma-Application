Read AGENTS.md, docs/PROJECT_SPEC.md (sections 6, 8.5, 12, Decision Log A22-A24, A53-A58), **docs/PHASE2_SPEC.md sections 1, 2, 3, 10**, docs/PROJECT_PHASES.md 2.3-2.4, docs/gates/gate-b8.md, and the existing `GroupAccessService`, `MemberService`, `GroupService`, `ExpenseService`, `SettlementController`. Prerequisite: Phase 1 (B0-B9) merged and green. Skills (max 4): think-before-coding, auth-and-authorization, data-modeling-discipline, migration-safety.

Why this exists: Phase 1 is owner-only (every group-scoped call goes through `GroupAccessService` and answers 404 to anyone but the owner). Every other Phase 2 prompt (invites, lifecycle, settlement v2, handles, notifications) needs members who are not the owner. Do the authorization change **first**, alone, so that all later prompts only add permissions to one component.

Step 0 (plan, wait for approval): the six-step design, and settle explicitly (record each in the Decision Log from A65 on and amend AGENTS.md invariant 7 + spec 8.5 where they say owner-only / never 403):
1. **Denial codes.** Recommended: not an ACTIVE member or unknown group -> 404 `NOT_FOUND` (IDOR defense unchanged); member without the permission -> 403 new code `FORBIDDEN` (add to `ErrorCode`, the OpenAPI `Problem` enum and `ApiContractCoverageIT`). Say how a `LEFT` member is treated (recommended: same as a stranger, 404).
2. **Permission model.** A `Permission` enum (one value per row of the PHASE2_SPEC section 2 matrix) and a `Role -> Set<Permission>` table in one place; the component exposes `requireMember(groupId)` and `require(groupId, Permission)` returning a `GroupContext` (group + caller's member + role). "Own expense" rules (edit/delete own vs others') need `created_by`: check whether `expenses` has the creator member/user and, if not, add it in this migration with a backfill (Phase 1 rows -> the group's owner member) and say so.
3. **Schema (V12, forward-only).** `members.role/status/joined_at/left_at` with CHECKs, one OWNER per group (partial unique index), backfill: the member linked to the group's creator -> OWNER, all others MEMBER/ACTIVE, `joined_at` = `created_at`. Review with `review-migration`; lock/rewrite risk of the ALTERs on populated tables; the migration must work on a database that already has Phase 1 data (test it with seeded V1-V11 data in Testcontainers).
4. **API shape.** `MemberDto.role`, `MemberDto.status`, `MemberDto.hasAccount`; `GroupDto.yourRole`; `GroupSummaryDto.yourRole`. Never expose account ids. `GET /groups` lists every group where the caller is an ACTIVE member (currently: groups created by the caller): change the query without N+1 and keep the `yourNetMinor` computation correct for non-owner members. **N+1 rules (from the pre-B10 scan):** the membership check is a join/`exists` predicate **inside** `ExpenseGroupRepository.findSummaries` (never a per-group call to the permission component inside a stream/loop); `MemberDto.role/status/hasAccount` come from the member row itself (`user_id is not null`), no per-member `users` lookup; own-expense permission/`canEdit` is computed in memory from the already-loaded rows and the caller's member id, never by a query per expense; `YourNetQuery` currently sums the whole ledger of the page's groups: restrict every union branch to the caller's member ids (`member_id in (select member_id from mine)`) while keeping it one statement.
5. **Existing endpoints.** Map every Phase 1 operation to a permission (table in the plan). Group edit/delete, member add/rename/delete, expense edit/delete (own vs others'), settlement create/delete stay as in the matrix; this prompt changes **who may call**, not what the endpoints do. Group create still makes the creator the OWNER member (A53).

Implement: migration, entities/repositories, the permission component (replace `GroupAccessService` call sites; delete dead code), `FORBIDDEN` handling in `GlobalExceptionHandler`, DTO/mapper changes, OpenAPI regeneration (`-Dopenapi.write=true`), `DevSeedRunner` (owner OWNER, others MEMBER, plus one ADMIN-capable second account for tests), README, Decision Log, ADR-009 "Role-based authorization" (short), AGENTS.md/CLAUDE.md invariant 7 text.

Tests (Testcontainers): **role x operation matrix** (parametrised: every existing operation x {OWNER, ADMIN, MEMBER, LEFT member, stranger, anonymous} -> expected 200/201/204/403/404/401, one assertion per cell; the test fails if a new route has no matrix row); IDOR cases unchanged for strangers (404, same body as unknown id); a MEMBER cannot edit another's expense but can edit their own; Admin can; exactly-one-OWNER constraint enforced by the database (direct insert fails); migration test with Phase 1 data; `yourNetMinor` still correct and N+1-free for non-owner members; **statement-count tests** in the style of `ExpenseListQueryCountIT`: `GET /groups` with 1 vs 50 groups (caller is OWNER in some, ADMIN/MEMBER in others) issues the same number of statements, and so do `GET /groups/{gid}`, the members list and the expenses list (with `canEdit`-style data) for 1 vs 50 rows; mass-assignment test (client cannot send `role`, `status`, `isYou`, `userId`). Existing tests may change only where authorization legitimately changes: list every changed assertion in the summary, never weaken one.
Constraints: follow AGENTS.md; no invitations, no lifecycle endpoints, no settlement changes here (B11-B13); engine untouched; no new dependency. Done when `./mvnw clean verify` passes. Then follow the Stop protocol and tell the owner that `mobile` must regenerate the client (`docs/mobile-client.md`).
