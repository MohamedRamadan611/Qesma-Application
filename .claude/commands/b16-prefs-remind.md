Read AGENTS.md, **docs/PHASE2_SPEC.md sections 3 (notification_prefs, remind_log), 8 (Remind), 10, 11**, docs/PROJECT_PHASES.md 2.7, the B15 recorder and notification tables, `BalanceService` (suggested transfers), `IdempotencyService`. Prerequisite: B15 merged. Skills (max 4): think-before-coding, idempotency-and-side-effects, query-discipline, error-handling-as-design.

Step 0 (plan, wait for approval): the six-step design, and settle (Decision Log):
1. **Prefs semantics.** Global `enabled` (default true) and per-group `muted` (default false). A muted/disabled recipient gets **no notification row**; the activity feed is unaffected. Does mute apply to `REMINDER` and to `SETTLEMENT_DISPUTED` (recommended: mute applies to everything except nothing; document it and the UI copy implication). Prefs apply at write time: say what happens to already-created notifications when the user mutes later (recommended: kept).
2. **Remind rules.** `POST /groups/{gid}/transfers/remind {fromMemberId, toMemberId}` with `Idempotency-Key`: caller must be the creditor's linked member or Admin/Owner; a suggested transfer for exactly that pair must exist **now** (compute it from the same balances path as `GET balances`, CONFIRMED-only rule from B13) else `VALIDATION_ERROR`; the debtor must be a linked ACTIVE member (a ghost has no account: decide the response, recommended 422 with a clear code reuse rather than a silent 204); not self.
3. **Rate limit.** One reminder per (group, debtor) per 24 h, source of truth `remind_log` inside the same transaction, race-safe (two parallel reminds: exactly one succeeds; use a unique-window technique or row lock and state which). Violation -> `429 REMIND_RATE_LIMITED` with `nextAllowedAt` in the problem body; add `canRemindAt` (nullable timestamp) to each suggested transfer in the balances view so the client can disable the button without guessing and without clock arithmetic on money.
4. **Endpoints.** `PUT /groups/{gid}/notification-prefs {muted}`, `PUT /me/notification-prefs {enabled}`, `GET` of both inside `GET /me` and `GET /groups/{gid}` (decide the minimal field: `UserDto.notificationsEnabled`, `GroupDto.muted`; no separate GET unless needed).
5. **Abuse.** Per-user reminder rate across groups (e.g. 20/day) to stop spam via many groups; justify the number.

Implement: migration V17, services, controllers, DTO additions, `ErrorCode.REMIND_RATE_LIMITED` (+ problem extension member `nextAllowedAt`, OpenAPI `Problem` schema, `ApiContractCoverageIT`), recorder integration (REMINDER event + notification to the debtor), OpenAPI + ids, README, Decision Log.
Tests: mute/disable suppresses rows but not feed events; unmuting restores; remind success creates one REMINDER notification for the debtor only; second remind in 24 h -> 429 with correct `nextAllowedAt`; after the window passes (controllable `Clock`) succeeds; parallel reminds (one wins); remind with no suggested transfer, wrong direction, self, ghost debtor, LEFT debtor; only the creditor or an admin may remind (member 403, stranger 404); idempotent replay does not create a second reminder or consume a second slot; `canRemindAt` correct in the balances view and computed for all transfers with one `remind_log` query (statement count constant for 1 vs 50 transfers); per-user daily cap; B10 matrix extended.
Constraints: follow AGENTS.md; no push (B18); a reminder never contains an amount the server did not compute; no new dependency. Done when `./mvnw clean verify` passes. Then Stop protocol; tell the owner `mobile` must regenerate the client.
