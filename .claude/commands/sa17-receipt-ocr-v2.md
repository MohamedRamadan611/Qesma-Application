Read AGENTS.md, mobile/AGENTS.md, `.claude/mobile/SCREEN_MAP.md`, docs/STANDALONE_SPEC.md sections 13 and 18.4 and Decision Log entries A144–A146, A169, A170, A176 (use Grep, read only those rows), `lib/features/receipt_scan/application/` (`firebase_receipt_reader.dart`, `receipt_reader.dart`, `parsed_receipt.dart`, `receipt_parser.dart`, `receipt_draft_mapper.dart`, `receipt_scan_service.dart`), `lib/features/receipt_scan/presentation/scan_flow.dart`, `lib/features/expenses/data/expense_category.dart`, the SA16 editor state (`ItemDraft.quantity`, discount, charge modes), `lib/core/money/money.dart`, `test/features/receipt_scan/`, and the guard tests. Prerequisite: SA16 merged. Skills (max 4): think-before-coding, testing-with-discernment, ux-copy, accessibility-review.

Why: a scanned receipt should fill what the editor now supports, so the user only confirms: quantity and unit price per item, the discount, the restaurant name as the title, and the category. The AI only proposes; the user confirms every number, and the model's arithmetic is never trusted.

Step 0 (plan, wait for approval): the six-step design with: (1) schema and prompt: add per item `quantity` and `unitPrice`; add `discountAmount`, `discountPercent`, `merchantName`, `category` (an enum of the section 7 values or null, the same list as `ExpenseCategory`); all numbers stay strings; the prompt keeps "copy numbers exactly as printed, never calculate, correct or guess"; how to read the Egyptian receipt wording for a discount (for example خصم) and for quantity columns; the model id constant stays in one place. (2) Parser: `Money.parse` / `Bps.parse` for the new strings; quantity through integer parsing clamped to 1..999, an unparseable or out-of-range quantity is flagged and the item opens as quantity 1; a line total with a quantity above 1 but no unit price is flagged `needsUnitPrice` for the user to confirm (the client never divides); a discount with both an amount and a percent keeps the amount and adds a note; a discount equal to or above the printed subtotal is dropped with a note; unknown category becomes null. (3) Draft mapper: discount into the SA16 draft (amount or percent mode); `merchantName` into the title only while the title is empty (trimmed, capped at the title limit); category only while the user has not chosen one; quantity and unit price into the items. (4) Scan notes and banners: new notes for quantity needs checking, unit price needs checking, discount found, discount dropped, name and category suggested; Arabic copy via ARB. (5) Privacy unchanged: the same consent, the same limits (20 scans per Cairo day), nothing stored; no new data is sent beyond the image. (6) Failure modes unchanged; an old-style model answer without the new fields still parses.

Implement per the approved plan with `ReceiptReader` still behind its interface so tests use a fake.

Tests first: parser table tests (quantity valid / 0 / 1000 / text; unit price missing; discount amount, percent, both, too large, Arabic-Indic digits; merchant empty / too long; category known / unknown / null; the old schema without the new fields); mapper tests (title and category filled only when empty or untouched; items with quantity; discount mode); scan UI tests for the new notes in ar and en and at text scale 2.0; a regression test that the existing receipts in `test/features/receipt_scan/` still produce the same draft; guard tests (no client-side division or other money math).
Constraints: no new dependency; no API key in the app; the model never decides a number. Done when `flutter analyze` and `flutter test test/features/receipt_scan test/features/expenses` pass, then the full `flutter test` once; list the manual device checks for the owner (a receipt with a quantity, a discount and a restaurant name; a receipt with none of them). Then Stop protocol; do NOT start SA13.
