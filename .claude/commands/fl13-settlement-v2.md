Prerequisite: FL12, B13 and B14 merged. Skills (max 4): think-before-coding, ui-ux-pro-max, ux-copy, accessibility-review.

Step 0 (plan, wait for approval): the design; mapping of every element to `BalanceView.transfers[]` (`pendingMinor`, `hasDispute`, receiver handles, `canRemindAt`) and `SettlementView` (`status`, timestamps, `recordedByAdmin`); **what replaces FL7's "record payment" and "delete payment"** (backend B13 removed the delete: cancel is the action; the recording sheet now declares a payment as PENDING for members and records CONFIRMED on behalf for Admin/Owner: say which controls each role sees); the exact copy of the pending vs confirmed explanation (balances count only confirmed payments; show both numbers from the server, never subtract on the client); who sees which action per status (payer: cancel while pending; receiver: confirm / not received; admin: all; dispute resolution); omitted elements: **attached transfer screenshot, transaction number, avatar photos, "bank transfer verified" labels** (no backend data); missing designs list.

Implement:
1. **Transfer card** for the current user as payer (P13-01): receiver name and server amount, receiver's InstaPay/wallet from the DTO with copy buttons, the fixed note "التطبيق مبيحوّلش فلوس — حوّل من تطبيق البنك أو المحفظة وبعدين اضغط دفعت", buttons "دفعت" (creates the PENDING settlement with `IdempotentAction`, amount prefilled from the transfer, editable for partial) and "نسخ البيانات". If the receiver has no handles: explain, still allow "دفعت".
2. **Receiver view** (P13-02): card "يوسف بيقول إنه دفعلك 720.00 ج.م" for PENDING settlements addressed to the user, buttons "استلمت ✔" (confirm) and "لسه مااستلمتش" (dispute, with a confirm), reachable from the balances tab and from the group home; result states and error handling (`INVALID_STATE_TRANSITION` -> refetch and show the current state).
3. **Status chips** everywhere a settlement or transfer appears: "في انتظار التأكيد" (amber), "مؤكّد" (green), "فيه خلاف" (red), cancelled (neutral): text + icon + colour, labelled for screen readers.
4. **Disputed detail** (P13-03): amount, both parties' statements as plain status text (payer says paid / receiver says not received) derived from status only, dates from the server, the guidance box (friendly resolution, the app does not arbitrate), actions "تأكيد واستلام الدفعة" (confirm) and "إلغاء الدفعة" (cancel) shown per role, visible to both parties and admins; the activity-log sentence only if B15 data exists (otherwise omit).
5. **Balances tab changes**: per-transfer pending badge from `pendingMinor` ("فيه دفعة في انتظار التأكيد"), dispute flag, "Remind" is FL14. Settlement history shows statuses and cancelled rows; remove FL7's delete-payment control and its tests.
6. Refetch after every action (balances, settlements, group); keys per action attempt.
7. ARB strings; extend scope-guard allow-list (`dispute` etc.) for this feature only.

Tests: parametrised role x status x action table (what is shown/hidden); copy buttons put exactly the handle on the clipboard; create PENDING key lifecycle; confirm/dispute/cancel flows with the 409 transition error; chips semantics (word + icon + colour); balances rendering from real backend-shaped V1/V2 fixtures **plus** pending/disputed fixtures (nets unchanged by pending, badge shown); no arithmetic guard (grep test that pending is never added/subtracted); widget tests ar/en/2.0; goldens for the transfer card, the receiver card, the disputed detail and the balances tab; omitted-element search test (no screenshot/transaction number).
Constraints: SCREEN_MAP rules; the app never moves money and says so; no payment-proof upload. Done when analyze and tests pass. Then Stop protocol; do NOT start FL14.
