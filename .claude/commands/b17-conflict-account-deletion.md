## Part A: conflict contract
Step 0 decisions: the `409 VERSION_CONFLICT` problem body gains `currentVersion` and `current` (the latest `ExpenseView` the caller is allowed to see, same shape as `GET expense`); for group edits (`PATCH /groups/{gid}`) the same with `GroupDto`. Say how the OpenAPI `Problem` schema models the optional extension without breaking the generated Dart client (a dedicated `VersionConflictProblem` schema referenced from the 409 responses is recommended). A conflict never leaks anything the caller could not GET. Tests: edit with a stale `If-Match` returns the latest values and version; delete with stale version likewise; stranger still 404, never a body with data; contract coverage updated.

## Part B: account deletion
Step 0 (plan, wait for approval): the six-step design, and settle (Decision Log) with an explicit **data inventory**: every table/column holding personal data of the user (users, passwords, email_tokens, refresh_tokens, payment_handles, notification_prefs, notifications, device_tokens, members.name for linked members, group_events payload actors) -> action (purge, anonymise, keep) and why. Recommended:
1. `DELETE /me` body `{confirm: "DELETE"}`; password accounts additionally send the current password (decide); response `204`; all sessions end in the same transaction (refresh tokens revoked, the access token expires within 15 minutes: say how it is rejected afterwards, e.g. check `deleted_at` in the token filter).
2. `users` row anonymised, not deleted (FK integrity): display name -> "Deleted user", email/username/provider subject replaced by a random tombstone so the original address can register again, `deleted_at` set; credentials, handles, prefs, notifications, device tokens, tokens deleted.
3. Members linked to the user keep their row, name and history and become `hasAccount = false` (ghost-like but flagged `deleted`; they must not be claimable by invite unless an admin unlinks: decide). **Every other member's balances and every ledger row are byte-identical before and after.**
4. Ownership: an Owner of a group with other ACTIVE members must transfer ownership first (`409 OWNER_MUST_TRANSFER`, list the offending groups in the body); a group where they are the only member and which is empty is deleted; the Owner of a group with history and no other active member: decide (recommended: block with the same code and explain).
5. Idempotent: a repeated call by a deleted user is `401`; concurrent deletion and login handled.
6. Retention note and open item "lawyer review of the retention approach" in the spec; Google Play account-deletion requirement noted (also needs a web page/URL: out of scope, list it as an open item).

Implement: migration V18 (`users.deleted_at`, CHECKs, any needed nullable columns), `AccountDeletionService` (`@Transactional`), controller route, token filter rejection, OpenAPI + ids, Decision Log, README, `docs/PHASE2_SPEC.md` privacy notes.
Tests (Testcontainers): conflict payloads (A); **balance-invariance test**: seed a group with expenses/settlements, snapshot `GET balances`/`GET expenses` for the other members, delete the account, assert identical JSON except the deleted member's `hasAccount`/display flag; purge assertions per table (zero rows for the user in each personal-data table); the old email/username can register again; sessions invalid after deletion; owner-must-transfer; sole-member empty group removed; replays and parallel logins; the deleted user's name does not appear in activity/notification payload reads; capture-appender test (no email/username in logs); B10 matrix extended.
Constraints: follow AGENTS.md; never hard-delete ledger rows; no email sending; no new dependency. Done when `./mvnw clean verify` passes. Then Stop protocol; tell the owner `mobile` must regenerate the client.
